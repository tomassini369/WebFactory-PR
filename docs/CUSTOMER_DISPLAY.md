# Customer Display: stage 4 increment

This extends the existing POS and `webfactory-client-commerce` Netlify Blobs store, using random opaque `pos-displays/{id}.json` keys. No additional application database, catalog, inventory or payment provider is created. PR #101 is independent and excluded.

The authenticated POS operator opens Customer Display in the existing POS checkout and generates a pairing link. The fragment contains a random 256-bit one-use secret, not cashier credentials. App initialization removes the fragment before page effects run. The second device explicitly confirms pairing; a conditional ETag write permits exactly one device. Only a hash is stored. The screen receives a separate Secure / HttpOnly / SameSite=Strict / host-only cookie and cannot use it for portal authentication. Links expire in 10 minutes and sessions expire after 8 hours. Revoke disconnects the device and clears sale data. The operator must still have a POS-capable membership for public reads. Platform administrators without a business membership cannot pair a screen on behalf of a member.

All private mutations require authenticated POS capability, same origin, the same tenant and immutable operator ID. Synchronization uses conditional writes and monotonically increasing sequences. Older messages cannot replace newer carts. Six bounded concurrency retries fail closed; the next heartbeat retries using a newer sequence. GET requests do not write attendance, payment or display records.

The cashier sends only item IDs, quantities, authorized discount/tip amounts and a sale-attempt reference. The backend resolves catalog prices and the existing tax calculator. Personal customer details, employee names, salaries, API credentials, checkout URLs and payment tokens are never included in the public DTO. A referenced transaction must belong to the same tenant, come from the existing POS and have the same cashier creator. In-person processing remains pending until completion. Stripe confirmation comes from existing backend transaction status, never from a screen button. Confirmed transactions supply the stored totals and redacted receipt identity/time. Printed receipt detail uses these stored values. Modifiers are not invented: the existing POS currently supplies simple item lines; business-specific modifiers remain a subsequent increment.

The screen polls every 3 seconds; the cashier sends a heartbeat every 5 seconds and debounces cart edits. Draft totals are labelled as estimates. After 20 seconds without cashier synchronization, the server hides totals and receipt data. Browser requests time out after 8 seconds, and a local connectivity deadline also hides old data. Refreshing the public screen preserves pairing through its cookie. Leaving/reloading the cashier workspace stops synchronization; revoke and generate a fresh link when resuming. One display pairing per browser profile is supported. Pairing on a new device replaces neither the catalog nor financial records.

There are ES/EN and Light/Dark controls, tenant identity/logo/accent, keyboard focus and 44px targets. The public screen has no portal navigation or sales mutation controls. Business-wide module enable switches, a device-management overview and scheduled deletion of expired ephemeral display records remain separate increments. Expired sessions are denied even before deletion; no financial records are deleted by this module.

QA uses isolated fixture businesses and storage, including real handler execution against an in-memory CAS store. Browser tests simulate the device cookie transport for local HTTP fixtures; preview checks run against deployed assets. No real customer sale, attendance or payment is made during QA. Unit/integration tests verify one-device concurrent pairing, revocation, expiration, operator/tenant isolation, stale-data hiding, role-gated amounts, authoritative transaction status and redaction. Existing POS, Workforce, Builder and portal CI remains required.
